# 助手执行交接的流程

用户只需表达“把这个任务交给 DSH / Codex”。已能使用本机文件与命令工具的助手执行下面的流程；用户无需编辑 JSON 或查会话 ID。本指南是操作约定，不会自动启动另一个宿主。

## 交接方

1. 依据当前用户要求填写 STATE：当前任务、已确认事实、未核验声明、尝试过的操作、未解决问题、下一步和限制。不要把自己说“已完成”当成完成证据，也不从关键词猜当前任务。
2. 明确实际工程目录，使用 `STATE.project` 或 `handoff --project`。原生会话的工作目录不一定是任务工程，不能直接用它代替。非工程任务可省略工程快照。
3. `context.files` 填本任务相关的工程内相对路径。`context.refs` 可选填当前原生会话中已经核对的事件编号；或用 `context.since` 明确当前任务起点。程序会记录编号来源，并保留完整原文。没有选取时会展示近期事件，不宣称理解了所有相关性。
4. `checks` 只填写真实运行记录，包括命令、退出码、时间和可选的工程内日志相对路径。程序只记录填报及日志哈希，不自动执行命令，也不替助手验证测试结论。
5. 确定本端真实用户会话 ID，执行 `handoff --from <本端> --to <目标端> --thread <ID> --state <STATE路径> --project <工程>`。不要选子代理记录，也不要在多聊天时盲用 latest。
6. 将输出的 `receiver_prompt` 转发给目标助手；它包含入口、准确包 ID 和收件箱路径。当前仍需用户在目标端发这条消息。

## 接手方

1. 按转发的指令 `take <包ID> --host <本端> --thread <自己的真实会话ID>`。首次绑定后，返回使用 `reply --host <本端>`，无需重新填写会话、目标、原包和状态路径。
2. 先读可编辑状态、FOCUS 焦点材料和工程核对结果。工程变动时，检查具体差异和当前文件，再决定继续哪一步；不能仅按旧日志中的测试结果判断当前工程正常。
3. 原目录不存在时，用 `take <ID> --host <本端> --project <当前机器目录>` 显式映射。快照不复制仓库、依赖、附件或密钥。验收目录和夹具根应尽量短；Windows 未启用长路径时，深层目录可能超出路径上限，可选择更短的验收目录或 --root，无需修改系统设置。
4. 修改程序输出的独立 STATE 草稿，保留任务约束和事实依据。若选取本端新增事件，context.origin填写本端host和已绑定thread；程序会读取该绑定会话并脱敏，明确标记为尚未封存的实时编号，不能拿它们去读接收的旧包。恢复时 take 会重新生成当前焦点材料，保留草稿，不把发送时的旧状态当成当前进度。
5. 交回时 `reply --host <本端>`。已绑定另一会话的任务不能静默换来源；明确继续该任务后，可 `take <ID> --switch --thread <新会话ID>` 重新绑定，原草稿保留。

跨宿主返回时，原生事件编号空间会变化。程序把原 `context.refs/since/origin` 移入 `evidence.previous_context`，附原包 ID；新的会话重新选取证据或使用近期片段，不能把旧 seq 当成新会话的 seq。

## 结束任务

核对完成后可将草稿 status 设为 done。无新来信时 take 仅显示已完成任务；有新来信时可接手最新一封，旧草稿保留。不必为“收到确认”持续来回发包。
